# CogniStream — Analysis Methodology

## 1. Objective

The analysis explores how recorded developer activity and context variables relate to cognitive-load scores and binary task outcomes. It is exploratory and observational. It is not designed to establish causation or diagnose a person's cognitive state.

## 2. Dataset and fields

The expected raw dataset contains 500 records and nine fields:

- Predictors: `hours_coding`, `coffee_intake_mg`, `distractions`, `sleep_hours`, `commits`, `bugs_reported`, and `ai_usage_hours`.
- Cognitive-load outcome: `cognitive_load`, expected to be on a 1–10 scale.
- Task outcome: `task_success`, expected to contain only 0 and 1.

The data-collection step checks the expected schema, missing values, duplicate records, and numeric/range rules. The cleaning step creates a processed copy and leaves the original raw CSV unchanged. Always regenerate the profile and analysis outputs for the exact dataset version used in a report.

## 3. Feature engineering

The feature pipeline creates descriptive bands for coding hours, sleep, cognitive load, and distractions. It also calculates:

- `distractions_per_coding_hour`
- `commits_per_coding_hour`
- `bugs_per_commit`
- `ai_hours_per_coding_hour`
- `task_success_label`

Bands are analyst-defined categories used to simplify visual exploration. They are not established psychological or medical thresholds. Ratio features with a zero denominator are undefined; they must not automatically be interpreted as zero. Confirm the code's treatment of undefined values before interpreting any rate-based result.

## 4. Descriptive analysis

The exploratory notebooks examine distributions, group summaries, and pairwise relationships. These views help identify data patterns and possible outliers, but visual differences alone do not establish statistical significance or causality.

## 5. Statistical methods

### Cognitive load by task outcome

The analysis compares the cognitive-load distributions for `task_success = 0` and `task_success = 1` using the Mann–Whitney U test. This non-parametric test evaluates whether values from one group tend to rank differently from values in the other group. It does not, by itself, test a difference in means.

A rank-biserial effect-size estimate is also reported. Interpret its sign using the exact group ordering and formula in `src/analysis.py`; interpret the magnitude alongside the group summaries rather than in isolation.

### Numeric predictors and cognitive load

Spearman rank correlation is used to estimate monotonic associations between each numeric predictor and `cognitive_load`. The coefficient ranges from -1 to +1. Values near zero indicate little evidence of a monotonic rank association in this sample, not necessarily no relationship of any kind.

### Numeric predictors and task success

Point-biserial correlation is used to estimate the association between each numeric predictor and the binary `task_success` variable. Its sign depends on the numerical coding of the binary outcome; the project uses 0 and 1. A positive coefficient therefore indicates that larger predictor values tend to align with the group coded as 1, subject to the data and coding being correct.

### Multiple-comparison adjustment

The Benjamini–Hochberg procedure adjusts p-values within the target-specific comparison families generated by the analysis. Prefer the adjusted p-value column when evaluating a set of related feature tests. State which p-value field is being reported.

## 6. Interpretation rules

1. Report the effect estimate and direction, not only whether a p-value crosses a threshold.
2. Include group sizes and descriptive summaries wherever available.
3. Do not describe an association as a cause or a predictive model as validated unless separate evidence supports that claim.
4. Avoid interpreting statistical significance as practical importance.
5. If a group is too small or a statistic is undefined, report it as unavailable; do not replace it with zero.
6. Confirm the actual report column names and values before writing numerical conclusions.

## 7. Limitations

The supplied data has no timestamps, session IDs, or developer identifiers. As a result, the current analysis cannot directly calculate uninterrupted flow-state duration, compare within-person changes over time, or separate repeated records from the same developer. A cognitive-load score is not, by itself, a direct measurement of flow state. The data collection process, sampling frame, and operational definitions also need to be documented before the findings can be generalized.
